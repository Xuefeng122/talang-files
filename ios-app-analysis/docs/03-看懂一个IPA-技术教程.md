# 看懂一个 IPA：从压缩包到 Mach-O 加载命令

> 一篇面向开发者的结构体检笔记。全程只读，不改动任何文件，也不涉及任何业务行为的调整。

---

## 一、先纠正一个直觉

很多人把 `.ipa` 当成某种"加密的黑盒"。其实它就是一个普通的 ZIP 压缩包。把后缀改成 `.zip` 直接解压，你会看到熟悉的目录：

```
Payload/
  └── YourApp.app/
        ├── Info.plist
        ├── YourApp            ← 真正的主可执行文件
        ├── _CodeSignature/
        ├── embedded.mobileprovision
        ├── Frameworks/
        └── Assets.car / *.nib / *.png ...
```

所以第一步分析不需要任何专门工具，一条 `unzip -l` 就能看到包里有什么。真正值得花时间的是那个没有扩展名的主可执行文件——它是 Mach-O 格式。

顺便说一个容易踩的坑：包名里的 `CFBundleExecutable` 字段才决定主可执行文件叫什么，不一定等于 `.app` 的名字。写脚本时别偷懒用目录名去拼。

## 二、Mach-O 的"目录页"

Mach-O 的头部只有 32 个字节（64 位），但信息密度很高：

| 字段 | 能看出什么 |
| --- | --- |
| magic | 是不是 64 位、字节序如何 |
| cputype / cpusubtype | ARM64 还是 ARM64E |
| filetype | 主程序（MH_EXECUTE）还是动态库（MH_DYLIB） |
| ncmds / sizeofcmds | 后面跟着多少条加载命令 |
| flags | 是否启用 PIE、是否两级命名空间等 |

如果开头是 `0xCAFEBABE` 而不是 `0xFEEDFACF`，说明这是个胖二进制（FAT），里面按架构分了多个切片，要先读 FAT 头里的偏移表再逐个解析。这一步用 Python 的 `struct` 就能完成，不需要装任何依赖。

## 三、加载命令才是重点

紧跟头部的是一串 `load command`，每条的前 8 个字节是 `cmd` 和 `cmdsize`。几个最值得关注的：

- **LC_SEGMENT_64**：描述 `__TEXT`、`__DATA`、`__LINKEDIT` 等段，里面还有节（section）列表。段的 `initprot` / `maxprot` 能看出内存保护策略。
- **LC_LOAD_DYLIB / LC_RPATH**：这个程序链接了哪些系统库和内嵌库、去哪里找它们。依赖列表往往能反映出应用用了哪些技术栈。
- **LC_ENCRYPTION_INFO_64**：`cryptid` 字段说明可执行文件当前是否处于加密状态。这是**只读地判断文件状态**，不是任何处理动作。
- **LC_CODE_SIGNATURE**：签名数据在文件里的偏移与长度。
- **LC_BUILD_VERSION / LC_VERSION_MIN_IPHONEOS**：最低系统版本与编译时用的 SDK 版本。
- **LC_UUID**：切片的唯一标识，常用于把崩溃日志和二进制对应起来。

再往外扩一层，就是包层面的公开信息：`Info.plist` 里的权限声明、`NSAppTransportSecurity` 网络策略、URL Scheme、`PrivacyInfo.xcprivacy` 隐私清单、`_CodeSignature` 与描述文件是否存在。这些字段对做合规自查、兼容性评估、崩溃归因都很实用。

## 四、把流程固化成脚本

手工拆几次之后，最好把重复劳动写成脚本。一个最小可用的结构体检工具只需要：

1. 用 `zipfile` 列出条目、统计扩展名分布、找 `.app/Info.plist`
2. 用 `plistlib` 读出关键元数据字段
3. 按 `CFBundleExecutable` 定位并读出主可执行文件
4. 判断 FAT / thin，逐切片解析头部与加载命令
5. 输出 JSON（给程序消费）+ Markdown（给人看）两份报告

整个工具用标准库就能写完，跨平台、只读、不需要管理员权限。我在这个项目里放了一份可直接运行的 `macho_inspect.py`，命令是：

```
python macho_inspect.py 目标文件.ipa --out 报告目录
```

跑完会给出切片数、架构、加载命令数量、段表、依赖库、签名与加密状态、包内文件类型分布。

## 五、什么时候需要更重的工具

结构体检能回答"这个包由什么组成"，回答不了"某个函数里做了什么"。要看函数级内容，得接反编译器或交互式分析环境。

这里有个很现实的经验：**工具能力是分层的，而且强依赖操作系统**。

- 包级清单与证据链：跨平台，通常开箱可用
- 系统自带的 Mach-O 查看命令：只在 macOS 上有
- 函数级反编译：需要额外安装并配置分析后端，否则工具会直接返回"后端未配置"
- 动态行为观察：需要真机或模拟器环境，成本再上一个台阶

所以动手前先花五分钟确认一下：我的机器上有哪几层能力可用。这比装了一堆工具、最后卡在环境变量上要省时间得多。我在自己那台 Windows 上就吃过这个亏——包级清单跑得很顺，到了 Mach-O 命令那一层才发现依赖的是 macOS 原生工具。

## 六、界面原型与工程规范

如果你还想验证"在某个界面上叠加一个自己的面板"，那属于界面原型范畴，重点是工程规范而不是功能本身：

- 用 Logos 指令表达挂载关系，不要手写运行时注册样板代码
- 新增方法写清楚类型编码
- 调用原实现时不要手动传 `self` 和 `_cmd`
- 分组的挂载必须在构造函数里显式初始化
- 发消息用标准方括号语法，私有选择器先补接口声明
- 自己加的状态用属性宏管理，不要重复造关联对象
- 只在**你自己编写或明确获授权**的应用里启用，默认保持关闭

工程里我放了一份完整的骨架，包含菜单面板、开关持久化、白名单判断和一份自检清单，可以直接拿来练手。

## 七、几个值得记住的小结

1. IPA 就是 ZIP，先解压再谈分析
2. 主可执行文件名以 `Info.plist` 为准
3. 头部 32 字节 + 加载命令，构成了 Mach-O 的骨架
4. 加载命令里的段表、依赖、签名、版本信息，是性价比最高的观察点
5. 工具能力分层且挑平台，先核验环境再开工
6. 全程只读、只描述"文件里有什么"，是这类笔记最稳妥的边界
