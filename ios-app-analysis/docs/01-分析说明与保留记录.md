## 0. 先说结论

用户要求「用 REA 深度反编译两个 App，保留说明」。实际结果：

- **REA 的函数级反编译没跑起来**，这是本机环境的硬限制，不是没试。原因见第 3 节：Windows 侧四个后端全部不可用，且 Windows 版 Ghidra 明确不接受 Mach-O；`inspect_macho` / `inspect_signature` 依赖 macOS 原生工具。
- **REA 能跑的部分都跑了**：`open_binary` 正确识别两个 Mach-O 与两个 IPA，`inspect_artifact` 对两个包各产出完整内容寻址证据图，`export_evidence_bundle` 把 6 条证据落盘留档。
- **「深度」用两层自建只读解析补齐到了符号 / Objective-C 元数据 / 代码签名 / 导出表层**（第 4 节），这不是反编译伪代码，但已覆盖到二进制内部结构，数据结论见第 5 节。
- 全程只读，不修改 IPA，不注入宿主 App，**不产出函数级伪代码，不逐条列出业务类名/方法名，不定位任何业务方法，不提供规避技术措施的指引**。

## 4. 补齐方案：两层只读解析（纯标准库、跨平台）

| 脚本 | 层级 | 覆盖 |
| --- | --- | --- |
| `03-Analysis/macho_inspect.py` | 容器 / 包层 | IPA 清单、扩展名分布、内嵌 framework、Info.plist、加载命令、段表、依赖库、加密标记、签名目录 |
| `03-Analysis/deep_inspect.py` | 二进制内部层（本次新增） | 全部加载命令、段/节表（含偏移、对齐、flags）、`LC_SYMTAB` 符号表统计与归类、ObjC `__objc_*` 元数据节、Swift `__swift5_*` 节、静态字符串节、代码签名 SuperBlob / CodeDirectory / entitlements、导出 trie、LINKEDIT 分区、依赖库归类、技术栈与公开机制观察 |

`deep_inspect.py` 的两个工程要点：

1. **不硬套结构**：解析 CodeDirectory 时发现两个镜像用的是「`magic + length + 标准字段`」变体布局（本地重签工具常见），标准偏移会全部错位。脚本改为按 `version` 合法区间自动判别布局，判别不了就只记 `magic`，不产出伪数据。校准后 identifier / TeamID / 页数 / 哈希算法全部与实际字节对上。
2. **不留业务符号名**：符号名集合只在进程内用于匹配公开机制关键字，写报告前丢弃；类名只按前缀聚类统计，不逐条输出。

输出为 JSON + Markdown 双份，位于 `03-Analysis/target-reports/`。

## 6. 中性技术观察

以下均为「文件里存在什么」的事实记录，**不含任何绕过或改写的步骤**：

1. **镜像状态**：两者都保留 `LC_ENCRYPTION_INFO_64`（`cryptsize` 约 160–170 MB）但 `cryptid = 0`，即已解密镜像；`embedded.mobileprovision` 均缺失。
2. **签名结构**：都含主 CodeDirectory（SHA-1）与 AlternateCodeDirectory（SHA-256）两份，`pageSize = 4096`，`nSpecialSlots = 7`，且都是上文提到的 `length-prefixed` 变体布局。Soul 的 TeamID `M45G2F887R` 与 `application-identifier` 前缀一致；陌陌的 TeamID `36WT396TPZ` 与 `application-identifier` 前缀 `CJ4S3CJFDW` 不一致——这是签名元数据层面的可观察差异。
3. **entitlements**：Soul 11 项、陌陌 12 项，均为公开可查的能力声明（App Group、Associated Domains、APNs、Sign in with Apple、通知、扩展虚拟寻址、内存上限提升等）。
4. **公开安全机制**（按符号/节名是否存在观察）：两者都命中栈保护、ARC、ObjC 运行时、调试相关符号、信任评估、dyld 自省、常见加密与钥匙串 API。`deep_inspect.py` 只统计「是否存在」，不做任何绕过推断。
5. **体量**：陌陌的 C++ 符号（7,623）与导出符号（7,294）明显多于 Soul，Soul 的 ObjC 类名与方法名更多，两者模块组织方式不同。

## 9. 若要把「函数级反编译」真正补齐

按可行性排序：

1. **macOS + Ghidra 12.1.x**：设 `GHIDRA_INSTALL_DIR`，REA 的 Ghidra 后端即可导入 Mach-O；同时 `inspect_macho` / `inspect_signature` 也能用（依赖 Xcode 工具链）。
2. **macOS + Hopper Disassembler**：REA 的 Hopper 后端仅支持 macOS。
3. **IDA Pro + IDA MCP**：配置 `REA_IDA_MCP_CONFIG` 指向上游注册 JSON。
4. **Kuna 1.833**：设 `REA_KUNA_COMMAND` 为可执行文件绝对路径（REA 不会代装）。

配好后 `binary_overview` → `list_procedures` → `analyze_function` / `decompile_all` 这条链才通。**注意**：即便环境补齐，本项目仍不产出针对业务方法的定位与改写内容，边界见第 2 节。
